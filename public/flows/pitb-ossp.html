PITB · Punjab Bureau of Statistics / OSS Online Statistical System / on-prem lakehouse

How the data platform
is actually wired

A metadata-driven warehouse that lands multi-sector government data into Delta Lake, models it as a star schema under Trino, then serves denormalised thin layers from ClickHouse. Airflow does not contain the graph — MySQL does.

01

The shape of the system

This repository is the code plane of Punjab’s OSS data platform: Airflow DAGs, SQL jobs, and a shared Python kernel. It runs on-prem under /edw/prod/code/ossp-data-platform-code/. Dev and prod are the same tree; an Airflow Variable named env chooses prefixes, hosts, and catalogs.

The lakehouse is not a single store. Raw and curated live as Delta tables on MinIO, queried through Trino catalog delta_lake (and delta_lake_secure for PII-heavy departments). Semantic staging is a Hive catalog write. Serving is ClickHouse. MySQL pitb_monitoring is the control plane: pipelines, tasks, ingestion parameters, watermarks, and operational logs.

02

End to end

Six stages. The DAG file only names a pipeline_id. Everything else — schedule, task list, bash command, upstreams — is loaded from MySQL at parse time.

01

Register the table

ops / metadata

automation/automate.py (and cousins) onboard a source table into pitb_monitoring.ingestion_metadata: department, source system, extraction type, watermarks, staging/raw DDL, merge column, masking, catalog id. task_metatable rows attach that table to a pipeline and order it.

Gate A raw task whose is_productionised = 0 is stripped from the DAG at parse time by generate_pipeline_dependency. Unpublished tables never run in prod by accident.
02

Land raw

dl_raw job

Airflow runs python Jobs/RAW/dl_rw_job.py <source> <db> <table> <env> <batch_id>. The job reads ingestion params, truncates staging, then branches on src_extraction_type × raw_ingestion_type:

  • full_load — Trino INSERT, or Sqoop for agri_smart / db_literacydrive (and the Hadoop path for health).
  • api + overwrite — generic API extractor, then append/overwrite into Delta.
  • cdc_one_watermark / cdc_two_watermark — stage the delta, then tbl_merge or tbl_append on raw.

Schema names are rewritten: delta_lake. becomes delta_lake.dd_ or delta_lake.dp_. Departments excisetaxation, citizen, pser (and a MySQL path) land in delta_lake_secure.

03

Build the star

ch_curated job

Jobs/Curated/run_ct_job.py loads a SQL file, substitutes :env / :start_date / :end_date / :batch_id / :table_name, and executes it on Trino. Layer tag in operational metadata: CURATED. Target schemas: dd_curated or dp_curated (_secure if the filename contains secure).

Sector DAGs usually fire in waves: Lookups → Dimensions → Facts. Helpings (*_hlp) are the bridge tables — citizen keys, location hierarchy, hospital keys — that facts join instead of hitting raw.

04

Copy into semantic staging

dl_ld job

Jobs/ldr/run_ld_job.py runs Trino SQL that deletes and inserts hive.:env_semantic_stg.<table> from delta_lake.:env_curated. That Hive write is the parquet landing MinIO later exposes as dd-semantic-stg / dp-semantic-stg (and -secure). Operational layer: SEMANTIC_STG. Vacuum on the curated Delta table follows unless opted out.

05

Serve from ClickHouse

ch_semantic job

Jobs/Semantic/run_sm_job.py injects an S3 parquet path (s3('…/dd-semantic-stg/<table>/2*', …, 'Parquet')) into the SQL as :input_path, then runs it with clickhouse-client on port 9440 (TLS). Thin-layer scripts (tl_*) truncate and rebuild denormalised dashboard tables in dd_semantic / dp_semantic.

06

Close the batch

control plane

end_batch (via dag_status, trigger rule ALL_DONE) writes pipeline status, clears the running mutex, and in prod emails a PITB list on failure. If the pipeline publishes an Airflow Dataset, downstream DAGs scheduled on that Dataset can fire.

Gate — mutex start_batch refuses to start if pipeline_metadata.running = 1. Two concurrent runs of the same pipeline are not allowed.
03

Airflow is a renderer, not a graph

Almost every file under Airflow/ is the same template with two literals changed: dag_number (the pipeline_id) and dag_id. commons/create_dag_file.py is the generator; the checked-in DAGs are the output.

task_description contains Runs Layer
dl_raw job Jobs/RAW/<args> — usually dl_rw_job.py Staging + Raw (Delta)
ch_curated job Jobs/Curated/run_ct_job.py … Curated (Trino → Delta)
dl_ld job Jobs/ldr/run_ld_job.py … Semantic staging (Hive / MinIO)
ch_semantic job Jobs/Semantic/run_sm_job.py … ClickHouse semantic
sit job Jobs/sit/run_sit_job.py … Curated-style Trino SQL (360-view / PIP marts)
trigger sh automation/<script> File-drop / wait-for-trigger
external_task_sensor Airflow ExternalTaskSensor Cross-DAG wait (same schedule required)

Scheduling

Cron comes from pipeline_metadata.pipeline_schedule. If pipeline_metadata_dependency.dependency_datasets is set, the DAG schedules on Airflow Datasets instead, and end_batch publishes dataset_name as an outlet. That is how Lookups → Dimensions → Facts chain without a giant single DAG.

What is not in the DAG file

Table lists, SQL paths, watermarks, and task order. Changing a pipeline’s graph is a MySQL edit (or pipeline_dependency_insert / _delete DAGs), not a Python PR — until someone regenerates the DAG to pick up a new dag_number.

04

Jobs: four folders, one star, one thin layer

SQL is the model. Python is a runner. Curated SQL is organised the way a warehouse team thinks: lookups, helpings, dimensions, facts — not by source system. Semantic SQL is organised by dashboard subject (hed_thin_layer, hmis_thinlayer, edu_thin_layer, …).

Jobs/RAW/
Generic lander plus API specialists. dl_rw_job.py is the JDBC/CDC/API router. Side folders cover eStamp, PRA, PFA, PLRA, PBS CSV, Excel.
Jobs/Curated/
Star schema on Delta. facts/ (~295 files), dimensions/ (~603), lookups/ (~93), helpings/ (~703). Runner: run_ct_job.py. Backfill twin: run_trino_backfill_job.py.
Jobs/ldr/
Curated → Hive semantic staging. Same grain as curated tables, often suffixed _ld. Copies keys and measures so ClickHouse can read parquet without querying Delta.
Jobs/Semantic/
ClickHouse serving + thin layers. Facts/dims mirrored, then tl_* denormalisations (program categories, location names, dashboard grains). Runners: run_sm_job.py, FDIP variants.
Jobs/sit/
SIT marts. Same Trino runner shape as curated. DAGs named for 360-views (schools, farmers, locations, CIS wing, commodities) rather than sector stars.

Curated object types

Lookups lkp

Small codes and reference lists (wards, blood groups, banks, roles). Loaded first so dims and facts can resolve keys.

Helpings hlp

Bridge / conformed-key tables. citizen_hlp maps source person ids to a warehouse citizen key. Location helpings land division / district / tehsil per department.

Dims and facts

Dims often MERGE on a business key. Facts INSERT with a surrogate (SUM(1) OVER (ROWS UNBOUNDED PRECEDING) on top of max_*_key). Audit columns: ins_tmstmp, upd_tmstmp, batch_id, oper.

05

A representative job: Health HMIS

One sector, four DAGs, the full layer walk. Education, Finance, Agriculture, HED, Dastak, Livestock, and FDIP repeat this shape. HMIS is the clearest because the SQL still shows the join from raw patients through helpings into a conformed patient dimension.

Patient dimension SQL is the pattern in miniature. It MERGEs into delta_lake.:env_curated.health_patient_dim from raw delta_lake.:env_health_hmiscentral_hmisv2centralproduction_raw.patients, joining citizen_hlp for the warehouse citizen key and location helpings for division / district / tehsil. Placeholders survive in git; the runner rewrites them. 

-- Jobs/Curated/dimensions/health_patient_dim/health_patient_dim.sql
MERGE INTO delta_lake.:env_curated.health_patient_dim AS target
USING (
  SELECT DISTINCT
    CAST(h.patient_key AS BIGINT) AS patient_key,
    CAST(HLP.citizen_key AS BIGINT) AS citizen_key,
    …
    ':batch_id' AS batch_id,
    'I' AS oper
  FROM delta_lake.:env_health_hmiscentral_hmisv2centralproduction_raw.patients p
  … join citizen_hlp, district / tehsil helpings
) AS source
ON target.patient_key = source.patient_key
-- WHEN MATCHED / NOT MATCHED  →  SCD-lite overwrite of attributes

Thin-layer SQL then lives on ClickHouse, not Trino. HED’s application thin layer (same idea as HMIS tl_health_hmis_*) truncates :env_semantic.tl_hed_application_details, inserts from the semantic fact, and adds dashboard grain — program category buckets, patched location names — that a BI tool should not recompute.

06

Flask is a product plane, not the control plane

Nothing under Flask/ starts a batch or writes task_metatable. Orchestration is Airflow + MySQL. Flask apps sit on the far side of ClickHouse (or a local MySQL copy of location dims) and answer HTTP.

Assan Karobar Card API

Flask/Assan_Karobar_Card_Api/main.py — bearer-token POST /api/has_registered_business. Reads ClickHouse view dp_ossp_integration.akc_pra_companies (join of secure PRA fact and citizen_hlp). Rate-limited. Gunicorn in non-local env. This is a consumer of the semantic layer.

Location API

LocationAPI (session login, MD5 against user_sign_in) and LocationAPIPublic serve division / district / tehsil reference data from a MySQL schema location_api. Used to maintain the location hierarchy the warehouse helpings also model — not to run ETL.

Where the real control plane is

commons/utilities.py plus configs/db_configs.py (AES-wrapped host maps for MySQL, Trino, ClickHouse, MinIO, and a handful of source DBs) plus configs/env_variables.py (schema names, monitoring table names, Great Expectations root, Spark/MySQL/Greenplum engine labels). Credentials are not documented here.

07

Trino, Delta, ClickHouse, MinIO

Encrypted config keys in ConfigManager are the inventory of engines: mysql, mysqlweb, trino, clickhouse, admin_clickhouse, minio, plus source aliases (agri_smart, db_health, db_literacydrive, tdas, fdip_clickhouse). Hostnames in DAG comments point at ossp-trino-dev.pitb.gov.pk and ossp-trino-coordinator-prod.pitb.gov.pk on 8443, catalog delta_lake. ClickHouse is TLS on 9440.

SQL token rewrite

add_arguements replaces :start_date, :end_date, :batch_id, :input_path, :table_name, and :env (dd or dp). That is why git SQL says delta_lake.:env_curated and production runs delta_lake.dp_curated.

Side engines

Kafka consumers stream special-education topics toward ClickHouse. trino_to_clickhouse.py and create_clickhouse_table map Trino types to MergeTree. Secure_Queries_Sync copies Trino/ClickHouse query logs into secure_*_logs tables. RBAC DAG generates CREATE ROLE / GRANT for ClickHouse from a web-backend roles table.

10

Decisions the code has already made

1. The graph lives in MySQL

DAG Python is a renderer. Task order, types, and SQL arguments are task_metatable rows. That lets ops change a pipeline without a deploy — and makes the repo look repetitive on purpose.

2. Two engines, not one lakehouse query layer

Trino owns Delta (model, MERGE, CDC). ClickHouse owns serving (thin layers, RBAC, APIs). Hive/MinIO parquet is the hand-off, not a third model.

3. Prefix, don’t fork catalogs

Dev and prod share catalog names. dd_ vs dp_ (and :env in SQL) is the isolation. Same job code, different rewrite.

4. Secure is a catalog, not a column

Citizen, excise/tax, PSER land in delta_lake_secure / *_secure schemas and MinIO buckets. Filename substring secure steers curated/semantic runners.

5. Thin layer is the BI contract

Dashboards are not expected to star-join ClickHouse facts. tl_* tables are truncated and rebuilt with grain, labels, and exception logic (HED tehsil 150 patches, program_category buckets).

6. Conformed citizen is the cross-sector key

Helpings and citizen_hub / citizen dims exist so Health, HED, livestock, zakat, ePay, PSER, and Dastak can share a person key without copying CNICs through every fact.

7. Batch mutex over Airflow pools

pipeline_metadata.running plus max_active_runs: 1. Backfill has a second table so a backfill cannot collide with the nightly run.

8. Sqoop remains for sources Trino cannot see

Health Hadoop and selected agri/literacy DBs: Sqoop → HDFS → Spark → MinIO, then the same Delta raw tables. Not a second architecture — a source adapter.

9. Flask does not orchestrate

Treat Location API and Assan Karobar as serving apps. Anyone looking for a “control API” will find MySQL metadata tables and Airflow instead.

10. README is not the architecture

Root README.md is still the GitLab template. This page is derived from runners, DAG templates, config keys, and representative SQL — not from that file.
