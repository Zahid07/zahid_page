A Flutter client talks JSON to a Flask API. The API does not invent SQL — it loads files from app/queries/allQueries/ and runs them against a PostgreSQL snowflake whose grain is one student on one trip.

01

The shape of the system

Trip Top is a student-trip marketplace. An organization (a student union, a travel club) publishes a trip. A customer (a student, often matched to a Finnish university email domain) books a seat. Staff belong to the organization. The schema comments still say TripMate; the Flutter shell, the Docker service, and this folder are Trip Top.

Three processes, one wire. They never share a database handle. They meet at HTTP.

One request, six hops

Blueprint → JSON body → getQuery.get_query(name) → preProcessParameters (:key replaced, longest first) → PostgresConnector (psycopg2, commit on every call) → jsonify.

Auth is issued, not enforced

Sign-in writes a JWT and a user_sessions row. require_auth exists. No registered route uses it. The admin home still sends Authorization: Bearer.

02

How the frontend talks to the backend

There is no generated client and no shared config object. Each Dart page constructs Uri.parse('http://<lan-host>:8080/api/v1/…') and calls package:http. Bodies are application/json. Lookups use GET; almost everything else is POST, including reads.

03

One API call, inside the process

Every blueprint copies the same path-append boilerplate so Windows and Linux can both import pgConnector, queriesClass, and preProcessParams. That is the whole data access layer.

04

End to end, in six stages

Order is causal, not decorative. A booking cannot exist without a published trip; a trip cannot exist without an organization; a student cannot exist without a role row in user_roles_lkp.

01

Register by role

wired

Three insert paths, three profile tables. Each looks up user_roles_lkp.role (admin / staff / customer), then does coalesce(max(id),0)+1 instead of letting SERIAL mint the key.

Student. Email is prefix@universities_lkp.domain. OTP (6 digits, 15 minutes, 3 attempts) must verify before /studentSignUp. The university id is written both as users.organization_id and customer_profiles.university_id.

Staff. Picks an existing organization. Profile verification defaults to Pending.

Admin. Creates the organization and the admin user in one request. Contact email becomes the user email. Admin profile is a row with is_superadmin left at default false.

Gate — student only OTP must be active, unexpired, under max attempts. Success sets verified, stamps verified_at, and deactivates the row.
02

Authenticate

issued not on routes

POST /sign_in matches email and password_hash as stored. On hit it mints an HS256 JWT (user_id, role_id, 24-hour exp), SHA-256s the token, and inserts user_sessions with IP and User-Agent. The JSON returns the raw token plus organization_id.

require_auth would: parse Bearer → verify JWT → hash → verifySession (active row) → expiry check → updateSessionAccess → stash g.current_user. require_role(*ids) would then 403. Neither decorator is applied on the 23 blueprints.

Gap Sign-up stores the password string in password_hash. Sign-in compares that string. update_user_data is the exception: it SHA-256s a new password. Those two representations cannot both succeed against signInUser.sql.
03

Read the catalog

wired

Public GETs fill dropdowns: universities (id, name, country, domain), organizations (id, name), roles. Authenticated-looking POSTs then list an organization's trips (select * from trips where organization_id = …), a trip's itinerary steps, a user's bookings (joined to trip title and dates), or a trip's booked/capacity counts.

The admin home filters Active / Closed in Dart by comparing start_datetime and end_datetime to now — not by trip_status_lkp.

04

Compose a trip

API only

Location first (locations_lkp, lat/long + JSONB metadata). Then /add_trips with org, creator, price, capacity, base location, window, status_id defaulting to 1 (draft in seed order), and optional JSONB metadata. RETURNING id comes back as trip_id.

Itinerary is not a JSON blob on the trip. It is ordered rows (UNIQUE (trip_id, step_order)). /add_trip_itinerary takes all_trips[] and inserts one by one. If a later step fails, it DELETE FROM trip_itineraries WHERE trip_id = … — all steps for that trip, not a SQL transaction around the batch.

Update trip / update one itinerary step / delete trip (CASCADE through itineraries, media, bookings) complete the write surface. The Flutter admin home does not call any of these yet.

05

Book a seat

API only

/add_booking is the fact insert. It refuses a second pending or confirmed row for the same (trip_id, user_id), refuses a trip that has already started, refuses a full capacity (pending + confirmed count against trips.capacity), and refuses price_paid below trips.price. A published-status check is in the file and commented out.

On success: secrets.token_urlsafe(32) becomes qr_token, expiry is start + 1 day, status_id is the lookup for pending. The unique constraint uq_trip_user_booking is the last line of defence. The handler returns the token in JSON; the follow-up RETURNING fetch is commented out, so the client does not receive the serial bookings.id.

06

Attend (QR + device)

schema only

devices stores a fingerprint hash, never a raw MAC — the schema comments say so, and warn that mobile OSes will not give you a MAC anyway. checkins records staff scan, scanner device, student device hash, optional coordinates, and the QR token used.

trip_media is the same kind of unused arm: table exists, no blueprint writes it. Seed SQL demonstrates a full check-in; Docker's new_seed.sql only loads lookups.

Not in /api/v1 No check-in, device-register, or media endpoint is registered. The ticket QR is generated at booking time and waiting for a scanner.
05

The snowflake

This is an OLTP database drawn as a snowflake, not a warehouse star. The fact is bookings: one row per student on a trip. Dimensions are normalized outward into lookup tables (*_lkp) and role-specific profile tables, so a name or a status code lives once.

That is the point of the split. A star would copy role, university, city, and itinerary steps onto every booking. Here a booking points at a user and a trip; the user points at a role and a profile; the trip points at a location, a status, and an ordered list of steps that themselves point at locations again.

Lookup codes, as seeded

TableCodesWho uses it
user_roles_lkp admin, staff, customer Every sign-up looks up by name. Flutter assumes ids 1 / 2 / 3 in that order.
trip_status_lkp draft, published, archived /add_trips defaults status_id to 1. Booking's published check is commented out.
booking_status_lkp pending, confirmed, cancelled New bookings insert pending. Capacity counts pending + confirmed.
customer_type_lkp domestic, exchange Seeded. customer_profiles in setup.sql uses is_exchange instead of this FK.
universities_lkp ~50 Finnish institutions, unique domain Student email construction and get_universities.

Two seed files, two truths

Docker init runs new_seed.sql — lookups only. seed.sql also builds a demo org, three users, a published trip, a booking, a device, and a check-in. It inserts customer_profiles.customer_type_id, a column setup.sql does not create. The live shape of a fresh compose is lookups plus empty core tables.

07

Decisions that are visible in the code

Snowflake, not a blob

  • Lookups for role, status, location, university.
  • Profiles off users so the core table stays slim.
  • Itinerary as ordered rows with a uniqueness constraint.
  • JSONB only where the shape is genuinely freeform (metadata, extra, social_media).

SQL files as the contract

  • One named file per operation.
  • Python does not assemble joins.
  • Flasgger docstrings on the handler are what the client was written against.

Ticket is a server token

  • QR payload is generated at insert, not by the phone.
  • Hash the session JWT at rest; store device fingerprints hashed.
  • Check-in designed around staff scan + student device hash.

Manual serials

  • Sign-up computes max(id)+1 even though columns are SERIAL.
  • Two concurrent sign-ups can collide. Trips avoid this with RETURNING id.

University as organization

  • Students put university_id into users.organization_id.
  • get_students joins that column to universities_lkp, not organizations.

Still open

  • Decorators written, not mounted.
  • Passwords not hashed on create/sign-in.
  • /generateOTP echoes the code in JSON.
  • A second, unused JWT decorator expects payload sub; the live issuer writes user_id.
08

What lives where

app/app.py
Process entry. load_dotenv, register blueprints, Flasgger, app.run(host=0.0.0.0, port=8080).
app/apis/
One file per route plus __init__.py which is the only registry. decorator.py and SkeyGenerate.py are not imported.
app/queries/allQueries/
The SQL. Named to match getQuery.get_query("…"). Loaded from cwd/app/queries/allQueries.
app/postgresConnector/
psycopg2 wrapper. Env-driven connect. Commit on success, rollback on error. No pool.
app/utils/
JWT, OTP, auth decorators, :param replace. SMTP settings live in otpHandler.py (not documented here).
database/setup.sql
Snowflake DDL. Lookups, core, trips, bookings, devices, checkins, updated_at triggers. Init script 01.
database/otp_table.sql
user_otps plus cleanup_expired_otps(). Init 02.
database/user_sessions_table.sql
user_sessions plus revoke / cleanup functions. Init 03.
database/new_seed.sql
Lookups only — what Docker actually loads (init 04).
database/docker-compose.yml
postgres:12 published at host 5433. Volume for data + the four init SQL files.
backend/docker-compose.yml
python:3.10 image, bind-mount ../app, pip from requirements.txt, listen 8080.
requirements.txt
Flask, psycopg2 / psycopg2-binary, flasgger, PyJWT, dotenv. Python 3.11.8 in the README; the backend image is 3.10.
09

What this author built

The snowflake and the API are the work in this folder: DDL, lookup seed, Flask blueprints, SQL files, JWT/OTP/session machinery, Docker wiring, and the booking invariants (capacity, uniqueness, start time, price).

The Flutter client is a sibling project. It implements welcome, three sign-up funnels, sign-in, an admin trip list, and itinerary detail. It does not yet call booking or trip-authoring endpoints, and staff/customer home is a placeholder.

Drawn from app/, database/setup.sql and companions, and the Flutter sources under trip_top_frontend_new/trip_top/lib. No values from .env. .venv ignored.
