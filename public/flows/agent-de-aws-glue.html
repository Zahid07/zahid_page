AWS Agentic DE / Oracle → Iceberg bronze → Glue silver

How the agent is written,
and how it works

A framework that encodes what this pipeline has already taught us, so a session starts knowing the rules instead of rediscovering them in CloudWatch three weeks later.

01

The shape of the system

Reference SQL is exported from the LDM into input/<module>/*.sql. A generator turns it into deployable Glue jobs. Those jobs build an Iceberg star schema on top of a bronze layer ingested from Oracle.

Three facts about this shape drive every rule that follows:

Generated output is not source

Everything under new_silver/ and every input/**/*.sql says Do not hand-edit. A defect there is a defect in the generator. Patch the artifact and the next run silently reverts you.

Correctness is checkable offline

The invariant audit needs no credentials and runs in seconds. It catches the class of bug that otherwise surfaces as a wrong number long after anyone remembers the change that caused it.

The agent prepares, the operator executes

Anything that changes AWS or deletes data is handed over as a command, not run. Credentials live in the operator's shell.

02

The flow

Five stages. The order is not a preference — each stage depends on the one before, and the gates between them are what stop a bad build reaching data.

01

Generate

offline

Reference SQL → job scripts plus a create_job payload. The load pattern comes from the SQL header's Construct / Key / Load fields, never inferred from a table name.

Scope is one module. --only narrows further and merges into the existing index rather than truncating it.

Gate Regenerating a module the operator did not name overwrites work they may be mid-review on. Confirm the scope before writing.
02

Audit

offline

Every generated script checked against the invariants: duplicate projection aliases, CTE ordering, decimal bounds, self-referencing DDL, JSON fold stability, dims that delete.

Gate — never skipped A failure here stops the pipeline. The fix goes in the generator and the module is regenerated; the artifact is never patched.
03

Deploy

operator runs

Script to S3, then create or update the job. The job block is passed to create_job verbatim — nothing is invented at deploy time. Dims before facts.

Gate --dry-run first, and show the operator the plan. They run the real thing.
04

Run in lineage waves

operator runs

Waves are derived from the jobs themselves — real joins recorded in readsSilverTables, plus raw FK carries — not from a hand-written list, so they stay correct as the module changes. Jobs inside a wave run in parallel.

Gate A failing job is reported, not retried, and everything downstream is skipped rather than run into a guaranteed failure.
05

Verify twice

destructive

Wipe, deploy, run, count, settle, run again, count again, compare. A second run over unchanged source must not change any row count.

A table that grows on run 2 is a real defect — a join fanning out, a duplicated SCD2 version, or a surrogate key being renumbered. That is exactly the class of bug this catches.

Gate — irreversible The wipe drops Glue tables and purges their S3 locations: Iceberg keeps metadata at the table LOCATION, so a catalog-only drop leaves snapshots for the next CREATE TABLE to inherit. It refuses to run without --yes, and refuses any S3 prefix not containing the table's own name. The agent never passes --yes.
03

What to write

The framework is six kinds of file, each doing a job the others cannot. The split matters: rules that belong in a hook do not work as prose, and knowledge that belongs in a skill is wasted in a hook.

CLAUDE.md
The contract. Loaded every session, so it holds only what is always true: ground rules, layout, the five load patterns, the twelve invariants in summary, and the destructive-operation protocol. Not a tutorial — everything here is load-bearing.
.claude/skills/*/SKILL.md
Deep knowledge, loaded on demand. One per task shape — generating a module, deploying, diagnosing a run, bronze ingestion, the invariants. The description is what decides whether a skill loads, so it names the symptoms, not the topic.
.claude/skills/sql-invariants/audit.py
Executable rules. A rule that can be checked by a script should be, not described in prose and hoped for. Offline, standard library only, non-zero exit so it drops into a pre-deploy gate.
.claude/hooks/*.py
Enforcement. guard_destructive blocks irreversible commands before they run; check_invariants catches a regression the moment a file is edited. Hooks are the harness acting, not the agent choosing — which is why the rules that must never be negotiated live here.
.claude/agents/*.md
Bounded reviewers. sql-auditor is read-only by construction, so it cannot alter what it inspects. log-forensics exists to separate a terminal error from recoverable noise.
.claude/commands/*.md
The sequences worth naming. /audit <module> and /ship <module> — the multi-step flows that are easy to half-perform from memory.
docs/INVARIANTS.md
The reasoning, kept. Every rule with the case that produced it, including one rejected approach — the window DELETE — recorded because a reasonable person will propose it again.

The test for where something belongs: if violating it is always wrong, it goes in a hook. If it needs judgment, it goes in a skill. If it is true of every task, it goes in CLAUDE.md. If it explains why, it goes in docs/ — where it can be long.

04

How the agent works

Behaviour is governed in three tiers, declared in .claude/settings.json. The tier a command falls into is a statement about reversibility, not about difficulty.

Allowed outright

  • Reading anything in the repo
  • --dry-run on every tool
  • The offline audit
  • Inspection: ls, grep, diff

Asks first

  • Generating a module (it overwrites)
  • deploy_job.py for real
  • Starting a run via watch_job.py
  • Editing anything in glue-tools/

Blocked

  • verify_module.py --yes
  • aws s3 rm, aws glue delete-*
  • Writing to new_silver/, silver/, input/**/*.sql
  • Reading credentials

Reading a failure

Most of the alarming text in a Glue log is recoverable. The agent ranks by log level, not by tone — and the driver/executor distinction resolves most Oracle questions on its own, because partition settings fan out on executors and never touch the driver's single connection.

SignalWhat it actually means
will be trying with next available connect option INFO, usually not the failure. The driver is walking a multi-address descriptor and failing over. It logs on every connection, forever, while the job works fine. A failure only when no address answers.
no log events at all Died at bootstrap and never reached the script — connections, or --additional-python-modules with no PyPI route in the VPC. This is why Run Details looks blank.
cancelled as part of cancellation of all jobs The DAGScheduler died. The real error is an IllegalArgumentException just above it.
ORA-17002, connect lapse 130 ms Connected, then died before auth — a network path, not a password. Usually one cursor streaming a whole table because a partition spec was half-configured.

Reporting

Outcomes are reported faithfully: a failure shows its output, a skipped step is named, and something verified is stated plainly without hedging. The agent never describes a run it did not see. Scope that was narrowed is always declared — a partial result stated is fine, a partial result implied is not.

05

The invariants

Twelve rules, each from a real defect. Severity is by failure mode, because it governs how hard to look: silent produces wrong data with no error, loud fails the job and announces itself, waste is correct but costly.

RuleSeverityThe case that produced it
Identifiers with # are backticked silent PRD_WTNOTE_DTL#2 truncated at the # and resolved to a different table that exists. The job succeeded and loaded the wrong data.
CDC watermark follows the predicate's qualifier silent A fact projecting tran_date from four tables read its watermark from t1 while filtering on d. The watermark drifts; rows are skipped forever.
SORT_ARRAY in every JSON fold silent COLLECT_LIST has no defined order. The JSON feeds row_hash, so an unstable string mints a new SCD2 version every run — the dimension grows with no source change.
Dead LEFT JOINs pruned, INNER never silent A dim declared six source tables; four supplied nothing. A LEFT JOIN matching more than one row silently multiplies the fact. An INNER filters rows even when it contributes none, so removing one changes the result.
Dims never DELETE silent SCD2 is insert-only. Deleting destroys history no rebuild can reconstruct.
cutoff captured before the DELETE silent Re-reading MAX() inline afterwards reads a table the delete already touched.
No duplicate projection alias loud 20 collisions across the corpus. A CTAS takes its column names from the projection, so two columns with one name is a table that cannot be created.
0 ≤ scale ≤ precision ≤ 38 loud Spark's ceiling. In a JDBC customSchema — parsed as one string — a single decimal(39,2) fails the whole table, not the column.
Never set spark.task.maxFailures loud Glue requires it strictly greater than maxTaskAttemptsPerNode (2). Setting it to 2 cancels every job at the first query, naming neither property. Cost an afternoon.
CTEs defined before use loud Generated _current CTEs were appended to the WITH list but referenced by an earlier one. Nine jobs affected.
Create-table DDL never reads its own table loud The watermark subquery, emitted into CREATE TABLE, reads a table that does not exist yet.
Ambiguous columns qualified loud WHERE item_code_nk IS NOT NULL where two CTEs both expose it.

One rule, three fixes

The duplicate-column rule is worth expanding, because it is the one where the obvious fix is mostly wrong. Three different causes hide behind one symptom:

CauseSeenFix
Same expression projected twice
s.cost_code AS cost_code ×2		 11 Keep the first, drop repeats. A prefix would leave two identical columns.
NULL placeholder beside a real expression
NULL + current_timestamp()		 5 Drop the placeholder. There is no table to name a literal after.
Different tables, same name
d.tran_date vs h.tran_date		 4 Prefix with the table's last name token → dtl_tran_date, mst_tran_date.

Applying the prefix rule to all three — the intuitive fix — would have corrected 4 cases and corrupted the other 16.

A worked example

The audit was run against all five generated modules while this framework was written. Four pass. One does not, and it is the useful one.

ModuleResultWhy
fgsPASSRegenerated after the duplicate-column fix
knittingPASS—
planningPASS—
sharedPASS—
finishing 14 findings Fact_Finopn and Fact_Cellwiseemp still carry duplicate active and tran_date columns — generated before the fix, and deliberately not regenerated.

That makes finishing the framework's own test case. It also carries the latent watermark bug: Fact_Finopn is CDC on TRAN_DATE and projects it from four tables, so deduplicating the aliases is what turns an invisible ambiguity into a choice that has to be made correctly. 

/audit finishing        # see the 14 findings and the warnings behind them
/ship finishing         # regenerate, re-audit, hand over the deploy commands
