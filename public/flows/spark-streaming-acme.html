How the analytics pipeline works

Four Kafka topics, four Spark Structured Streaming queries, one PostgreSQL instance split into operations and analytical. Change data capture from the WAL becomes a queryable dimensional model every ten seconds.

01

The shape of the system

ACME Delivery Services needed near-real-time answers over a living order book: open orders by delivery date, the busiest upcoming dates, pending items by product, and the customers with the most pending orders. The starter stack already wrote those orders into PostgreSQL. The work was to stream every insert and update into a dimensional schema that those four questions can hit without scanning OLTP.

Source and sink share one Postgres, two schemas. operations is the transactional system of record. analytical is the warehouse Spark writes. They never share tables. They meet only through Debezium, Kafka, and the four streaming queries in implementation/main.py.

Must-haves this shape serves

Current order state lives in fact_orders. Full change history lives in *_history (SCD Type 4). Ten-second micro-batches keep the dashboard within one trigger of the WAL.

Implementation code, DDL, connector JSON, compose files, and EXECUTION_README.md. Where the solution PDF disagrees with the repo, the code wins.

03

The flow

Eight stages. Order is load-bearing: Spark joins an external Docker network the core stack creates, and the dashboard assumes Postgres is already accepting connections on the host.

01

Source OLTP writes

operations

Four tables in operations: customers, products, orders, order_items. Each has REPLICA IDENTITY FULL so Debezium can emit a complete before image. A stored-procedure generator seeds the database and then pg_cron keeps it moving:

update_customers(5) every 2 minutes, update_products(10) every 2 minutes, generate_orders(100) every minute. New orders start as PENDING with delivery_date = CURRENT_DATE + 10; later updates pick PROCESSING, COMPLETED, or REPROCESSING.

Source line items store quantity in a column named quanity — a typo in the starter DDL. That spelling is the reason _additional_columns exists as more than a drift hedge.

02

Logical decoding

WAL

Postgres starts with wal_level=logical. Init SQL creates replication slot cdc_pgoutput (plugin pgoutput) and publication cdc_publication for all tables. A dedicated replication user cdc_user is granted CONNECT, schema USAGE, and SELECT on operations.

03

Debezium connector

Kafka Connect

debezium-init waits until Connect answers /connectors with HTTP 200, then POSTs finance-db-connector.json. Topic prefix is finance_db. Include list is the four operations tables. JSON converters run with schemas disabled. The slot is not dropped on connector stop.

Start order Core compose must be up before Spark. Connect must be healthy before the init container can register the connector. Spark reading empty topics is fine; Spark reading a missing broker is not.
04

Four Kafka topics

log

Topic names are <prefix>.<schema>.<table>, matching implementation/config.py:

finance_db.operations.customers, finance_db.operations.products, finance_db.operations.orders, finance_db.operations.order_items.

Inside Docker, Spark uses kafka:9092 (the INSIDE listener). On the host, config.py defaults to port 9094 (OUTSIDE). That split is why local spark-submit and the containered consumer do not share a bootstrap address.

05

Four Spark queries, one session

local[4]

main.py validates the analytical schema, builds a SparkSession named acme-analytics, and starts all four streams. It then awaitAnyTermination(). Each query reads from earliest offsets, sets failOnDataLoss to false, checkpoints under ./checkpoints/<entity>, and triggers every 10 seconds.

local[4] is intentional: four concurrent streams, four threads, so a JDBC write in one query does not starve the Kafka readers of the others. Shuffle partitions are 2. Checkpoints live on the spark-checkpoints volume so a container restart resumes offsets.

06

Staging overwrite, then MERGE

foreachBatch

Spark JDBC cannot upsert. Every micro-batch therefore: drop op, coalesce(1) so there is one JDBC connection, overwrite the staging table, run INSERT … ON CONFLICT DO UPDATE via psycopg2, append the same staging rows into the history table where one exists, then TRUNCATE staging. Truncate failure is a warning — the next overwrite replaces the table anyway.

Staging tables are LIKE … INCLUDING DEFAULTS EXCLUDING CONSTRAINTS so a child row can land before its parent without a foreign-key failure. That is how the design absorbs CDC ordering lag.

07

Dimensional warehouse

SCD 4

Current-state tables: dim_customer, dim_product, fact_orders, fact_order_items. History tables for customers, products, and orders. No history table for order items. Every current-state row also stores _kafka_offset and _additional_columns.

08

API and dashboard

10 s poll

FastAPI exposes four versioned GET routes. Each runs SQL against analytical tables and returns contract_version, generated_at, and data. React validates that shape before render and polls on the same 10-second cadence as Spark.

04

What a CDC event becomes

utils/debezium.py owns the envelope. Each consumer passes only its table schema. The helper wraps that schema as both before and after, parses Kafka value as JSON, and keeps c (create), u (update), and r (snapshot read). Deletes (op = d) are dropped. Soft delete is is_active on the dimension, not a hard remove from the warehouse.

The quanity column

Spark’s order-item schema names the field quantity. The source column is quanity. from_json therefore leaves quantity null, and the leftover key is serialised into _additional_columns. The MERGE writes COALESCE(s.quantity, 0) into the typed column. The pending-items API reads the real figure with COALESCE((_additional_columns::json ->> 'quanity')::INTEGER, oi.quantity, 0). Schema drift handling is not hypothetical here — it is how Q3 gets a number.

05

One micro-batch, four consumers

The four process_batch functions are the same skeleton with different SQL. Products and customers also write history. Orders write history and treat a history-insert failure as fatal. Order items skip history, denormalise order_status from fact_orders, and run a status-sync UPDATE even when the Kafka batch is empty.

QueryKafka topicCurrent tableHistoryExtra
products_stream …products dim_product yes, non-fatal on error DISTINCT ON product_id
customers_stream …customers dim_customer yes, non-fatal on error DISTINCT ON customer_id
orders_stream …orders fact_orders yes, raises on error status defaults to unknown
order_items_stream …order_items fact_order_items none LEFT JOIN orders + status sync
06

SCD Type 4, and why status is copied

Current-state tables are upserted. History tables are append-only point-in-time snapshots with recorded_at DEFAULT NOW(). That split is SCD Type 4: a current table you can filter fast, a history table you can replay an order’s lifecycle from. There is no Type 2 valid_from / valid_to on the dimensions.

07

Four questions, four contracts

The dashboard is four panels, not one mega-query. Each panel has a FastAPI route, a JS contract, and a 10-second poll. Delivery Status is the only panel that hides the loading spinner after the first fetch so the table does not flicker.

QUIRouteSQL, as coded
1 Delivery Status /api/v1/order-delivery-summary fact_orders where status not in COMPLETED, grouped by delivery date and status
2 Top Delivery Dates /api/v1/top-delivery-dates Same open-order filter, grouped by date, ORDER BY open_order_count DESC LIMIT 3
3 Pending Items /api/v1/pending-items-by-product Items joined to orders (PENDING) and dim_product; quantity from _additional_columns.quanity then quantity
4 Top Customers /api/v1/top-customers-pending-orders fact_orders joined to dim_customer where status is PENDING, top 3

Views are in the PDF, not in the DDL

The solution document describes four PostgreSQL views (v_open_orders_by_delivery and siblings) and claims the API contains no raw SQL. initialize_analytics_ddl.sql creates no views. visualization/backend/main.py embeds the four queries. This page follows the running API.

08

How you start it

From EXECUTION_README.md. Ports that must be free: 3000, 5432, 8001, 8083, 8087, 9094. Spark UI is 4040. 

# Terminal 1 — repo root. Core stack first so finance-shared-net exists.
docker compose up -d --build
docker compose -f docker-compose-spark.yaml up -d --build

# Terminal 2 — dashboard. Postgres must already be on localhost:5432.
cd visualization
docker compose up -d --build

Stop in reverse: visualization, Spark, core. Full reset adds -v so the Spark checkpoint volume and Postgres data both go. Without that, Spark resumes Kafka offsets and Postgres keeps generated orders.

Local spark-submit without Docker is documented in spark-submit.txt and uses Kafka 9094 plus localhost Postgres. The container CMD uses Spark package spark-sql-kafka-0-10_2.12:3.5.0. main.py’s session builder lists 3.5.1 — that line only matters for a host-side submit that relies on spark.jars.packages.

09

Decisions that shaped the code

Sink

foreachBatch + staging + ON CONFLICT, not a streaming JDBC append

Append would duplicate every update. Spark has no native JDBC upsert. Staging is the batch boundary; MERGE is the idempotent write; history is a second statement on the same snapshot of staging.

Rejected: foreachBatch straight into the target table. Concurrent partitions hung JDBC in local mode — hence coalesce(1).

History

SCD Type 4 instead of Type 2 on the same row

Current queries (Q1–Q4) only need latest state. Lifecycle questions need every CDC event. Two tables keep those access patterns from fighting each other. Order items have no history table; Q3 is a current-state quantity.

Trade-off: history grows with every source update. There is no compaction job in the repo.

Deletes

Drop op = d; treat inactivity as is_active

The generator toggles is_active with updates. Hard deletes are not part of the simulated workload. is_delete() is unused.

Gap: a real DELETE FROM operations.customers would leave the dim row in place.

Drift

Keep unknown payload keys as JSON rather than failing the parse

The quanity typo made this mandatory. New source columns ride along until someone adds them to the Spark schema and DDL.

Not built: the connector image enables Apicurio converters, but the connector JSON uses schema-less JSON converters. There is no registry in the running path.

Parallelism

local[4], shuffle 2, one JDBC connection per batch

Four streams need four threads. Default 200 shuffle partitions would spawn empty tasks on tiny micro-batches. Multiple JDBC partitions hung writes during development.

Ceiling: this is a laptop-sized take-home, not a cluster sized to Kafka partitions.

Latency

Ten-second trigger, ten-second UI poll

The dashboard cannot be fresher than the sink. Matching the intervals means a poll usually sees the latest completed batch rather than spinning faster than Spark can MERGE.

Contracts

Validate API JSON in the browser before drawing a table

Each report module has an isValid… checker. A backend change that drops a field shows as an error state instead of a blank or NaN cell.

Limits that are in the code

  • Hard deletes never reach the warehouse.
  • Foreign keys were left off analytical facts so CDC can arrive out of parent/child order.
  • Spark-side window dedup is commented out; latest-wins is the SQL DISTINCT ON.
  • Product and customer history insert errors are logged and swallowed; order history errors abort the batch.
  • Startup validation does not require history tables to exist.
  • JDBC session timezone is set to Europe/Kyiv while the database container is TZ=UTC.
  • Serving is a poll, not a push. FastAPI has no WebSocket.
