activate-customer-consumer-python / Customer Group Evaluator

How a queued group
becomes membership

A Python Kafka consumer that turns one group_id into a ClickHouse WHERE clause, a matched/unmatched delta, and three Kafka streams. It evaluates. It does not write the sinks.

Python 3.12 confluent-kafka MySQL 8 · ClickHouse Kafka fan-out × 3
01

The shape of the system

Merchants define automatic customer groups as a set of conditions in MySQL (salla.groups + salla.customer_group_conditions). When a group is eligible, a Timeplus materialized view emits a Kafka event carrying only a group_id. This service consumes that event, compiles the conditions into ClickHouse SQL, scores every customer in the store against the current profile, and publishes the delta — who should join, who should leave, and that the group is now active.

The repository logger calls itself evaluation-syncer. Architecture docs call it group-evaluation-consumer-python. The image is data/activate-customer-consumer-python. Same process.

This service owns

  • Consume group_id events
  • Compile conditions → ClickHouse SQL
  • Score matched / unmatched deltas
  • Publish three Kafka topics

It reads, never writes

  • MySQL salla.groups
  • MySQL customer_group_conditions
  • MySQL condition_relationships
  • ClickHouse profiles + current membership

Sinks own the writes

  • MySQL customer_groups_v2
  • OpenSearch auto_groups
  • MySQL groups.status
02

The flow, end to end

Eight stages. The first two happen before this process wakes up. The last happens after it has flushed. Everything in the middle is process_group.

01

Timeplus decides eligibility

upstream · not this repo

Materialized view mv_k_tp_groups_customer_groups_trigger_v2 emits only when the group is not expired and status = queue. A group that is already active, deleted, or past expired_at never becomes a Kafka message.

Boundary This consumer does not re-check those predicates. An arriving group_id is treated as authorized work.
02

Kafka input

topic from env

consumer.py reads KAFKA_TOPICS (plural). If unset, it falls back to prod.opensearch_customers.customer_groups_groups_trigger_v2. Each message is JSON with an integer group_id. Offsets reset to latest; auto-commit is off.

Env name README and .env.example document KAFKA_TOPIC. The running consumer reads KAFKA_TOPICS.
03

Worker pool

this service

A ThreadPoolExecutor with EXPORTER_HANDLER_BATCH_CHUNK_SIZE workers (default 5) runs process_group in parallel. In-flight is capped at KAFKA_MAX_IN_FLIGHT (default CHUNK_SIZE × 2): when the map is full, polling pauses. A group_id already in the map is skipped and its duplicate offset is committed.

The offset of a message is committed on the main thread only after that group’s future is done — success or exception. SIGINT / SIGTERM set running = False, drain in-flight workers (300s timeout each), commit, then close.

04

Fetch definition from MySQL

read

Three queries, three connections (connect / cursor / close each time):

  • salla.groups by id, deleted_at IS NULL — takes store_id and operator_type
  • salla.customer_group_conditions for the group, not deleted, type != '', ordered by id
  • condition_relationships where deleted = 0 — keyed by condition_name

If the group row has no store_id, customer scoring is skipped and nothing is published. Query SQL is overridable via MYSQL_GROUP_QUERY and MYSQL_GROUP_CONDITIONS_QUERY.

05

Compile a WHERE clause

QueryGeneratorService

Related condition types are grouped first (payment method with returned orders; purchased product with days-since-purchase). Standalone conditions become fragments. Fragments are joined by operator_type. Empty condition lists compile to 1 = 0 — match nobody.

06

Score in ClickHouse — as a delta

not a full recompute

Both queries join customer_profile.customer_profile (AggregatingMergeTree-style maxMerge / sumMerge) to customer_profile_extended (argMax(..., _ver)), filtered to the store. Then they consult local_salla.customer_groups_v2 FINAL for the current group:

  • Matched — satisfies WHERE and is not already in the group → assign
  • Unmatched — fails WHERE and is already in the group → delete
Why this is cheap Customers already correctly in (or out of) the group produce no event. Re-evaluating a stable group is a no-op at the sink.
07

Fan-out to three topics

GroupAssignmentService

One producer. Per matched customer: an OpenSearch upsert and a MySQL-sync upsert. Per unmatched customer: a MySQL-sync delete only — OpenSearch is not told about leavers. Then one status message sets salla.groups.status to active. flush(30) before return.

08

Connectors write the systems of record

downstream · not this repo

mysql_kafka_sink_connector upserts and deletes salla.customer_groups_v2. The OpenSearch indexer patches auto_groups on the customer document. mysql-sink-connector-python applies the group status update so the group leaves the queue state that Timeplus watches.

03

How the consumer loop actually runs

The loop is a single thread that polls, submits, and commits. Workers never touch the consumer. That split is why shutdown can drain without committing an unfinished group.

04

One group, inside process_group

executors/consumer_executor.py is both the worker body and a CLI. Services are constructed from the environment on every call — a new MySQL connection set, a new ClickHouse client, a new Kafka producer — then discarded.

Default operator_type in the executor

Before the group row is read, operator_type is set to 2. In OperatorType that is UNION (OR). The MySQL column default, and QueryGeneratorService.generate_where_clause’s own default, is 1 — INTERSECT (AND). The executor default only applies when the row is missing operator_type; a normal row uses the stored value.

05

Conditions become SQL

QueryGeneratorService is a compiler. ConditionRelationshipResolver is the first pass: if a condition’s type is a key in condition_relationships and at least one partner type is also on the group, those rows become a RelatedConditionSet (intersect or union). Everyone else is standalone.

operator_type Int Join
INTERSECT 1 Fragments joined with AND. Schema default. README numbers this as UNION — the enum and the MySQL column comment are the source of truth.
UNION 2 Fragments joined with OR.
DIFFERENCE 3 First fragment AND NOT (OR of the rest). A single fragment is kept as-is.
COMPLEMENT 4 NOT ( fragments joined with OR ).
anything else — _normalize_operator_type falls back to INTERSECT.

Related sets the builder knows by name

Unknown combinations fall back to independently built fragments joined with AND or OR according to the relationship type. Two combinations have dedicated SQL so the old Python evaluator’s semantics survive:

PairSQL shape
payment_method ∩ payment_returned_orders has(payment_methods, …) for each method, and the sum of toFloat64(payment_method_returned_orders[method]) compared to the returned-orders threshold. Seeded in scripts/mysql-init.sql.
purchased_product ∩/∪ product_purchased_days Presence via mapContains(product_last_purchases, toUInt64(id)), then least (intersect — all products within N days) or greatest (union — any product within N days) of dateDiff('day', …).

Standalone fragment kinds

ConditionFragmentBuilder maps condition type to a profile column, then symbol to a SQL operator. Empty values become 0 before specialized builders run. Placeholders are %s, bound later by clickhouse_connect.

Numeric / scalar columnstotal_sales → sales_total, total_orders → sales_count, have_cancelled_orders → canceled_orders_count, plus city, country, gender, dates, returned_orders.
*_daysdateDiff('day', toDateTime(column), now()) after mapping birthday_days / joining_date_days to the base timestamp column.

06

The ClickHouse delta

The profile side is the same CTE in both queries: extended fields rolled up by argMax(..., _ver) for the store, then a LEFT JOIN onto the aggregating customer_profile grouped by (store_id, customer_id). What differs is the outer WHERE and the membership subquery against local_salla.customer_groups_v2.

fetch_customer_profiles — a pair-wise merge of the two profile tables into a CustomerProfile dataclass — exists on ClickHouseService and is unused by process_group. Evaluation goes through the combined SQL templates in services/clickhouse/queries.py.

07

What goes on the wire

README still describes two output topics. The producer has three. Defaults below are the code fallbacks when env is unset — production overrides them.

Env Default topic When Key Body Downstream
KAFKA_OPENSEARCH_TOPIC customer-groups-opensearch Each matched customer {customer_id}_{store_id} id, auto_groups: ["{group_id}"], updated_fields: ["auto_groups"], is_new: 0. Leavers are not published here. OpenSearch indexer
KAFKA_MYSQL_TOPIC customer-groups-mysql-sync Matched → upsert; unmatched → delete {customer_id}_{group_id} Envelope: type, table: customer_groups_v2, database: salla, service: clickhouse_auto, where_clause on customer/group/source: auto. Upsert also carries created_at / updated_at UTC ISO. mysql_kafka_sink_connector
KAFKA_MYSQL_ACTIVE_UPDATER_TOPIC prod.active_group_updater Once per successful evaluation with a store_id group_{id}_status Upsert salla.groups where id, data { "status": "active" }, same service: clickhouse_auto envelope. mysql-sink-connector-python

OpenSearch payload is this group only

auto_groups is sent as a one-element array containing the current group_id. This service does not read the customer’s existing groups. Merge-or-replace is the indexer’s job. Because deletions never hit this topic, search documents can stay stale unless some other path removes the id.

09

Decisions that are load-bearing

These are not style. Change one and membership, lag, or a downstream connector changes meaning.

Evaluate the delta, not the set

ClickHouse already knows who is in customer_groups_v2. Publishing the full match set every run would thrash MySQL and OpenSearch. The IN / NOT IN subqueries are the contract with the sinks.

Commit after the worker, not after poll

enable.auto.commit is false. A crash mid-evaluation redelivers the group_id. At-least-once. Sinks must tolerate a repeated upsert; a repeated delete of an already-removed row is the connector’s problem.

Eligibility is upstream

Timeplus filters queue and expiry. This process would happily evaluate an expired group if someone published the id. That is a feature of the boundary, not a missing if.

Empty conditions match nobody

1 = 0 means a group with no live conditions assigns nobody and, via unmatched, removes everyone currently in it (who is in customer_groups_v2 for that group).

OpenSearch is assign-only

Leavers are MySQL deletes only. Search membership can diverge from customer_groups_v2 unless another job repairs auto_groups.

Status flip is part of evaluation

send_group_status_update runs after assignments and deletions, still inside the same store_id branch. The group is marked active even if both customer lists were empty.

Docs lag the code

README: two output topics, KAFKA_TOPIC, operator 1 = UNION. Code: three topics, KAFKA_TOPICS, operator 1 = INTERSECT. Trust OperatorType, GroupAssignmentService, and consumer.py.

Env names are not symmetric

MySQL user/database in code: MYSQL_USERNAME, MYSQL_DATABASE_NAME. Example file: MYSQL_USER, MYSQL_DATABASE. A local .env copied from the example will connect as empty user/database unless renamed.

10

Stack

Runtime is Python 3.12. Kafka client is confluent_kafka (librdkafka). MySQL is mysql-connector-python. ClickHouse is clickhouse_connect over HTTP (8123 by default). Config via python-dotenv.

Local compose brings Kafka advertised on 9094, a MySQL 8 with the salla seed, ClickHouse 23.8, and Conduktor on 8087. Production Kafka uses SASL_SSL / SCRAM-SHA-512 when WORKER_ENV is production or stage. Images land in ECR as data/activate-customer-consumer-python from .github/workflows/build.yml (eu-central-1).

Upstream of the input topic: Timeplus, itself fed from the customer / groups event path. Downstream of the three output topics: the MySQL Kafka sink connector, an OpenSearch indexer, and mysql-sink-connector-python. None of those are in this repository.

Drawn from consumer.py, executors/consumer_executor.py, services/, docker-compose.yml, and the SQL templates — not from the README where the README disagrees.
