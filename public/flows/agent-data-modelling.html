Case study — agentic data engineering

Reverse-engineering a database nobody documented

An eight-stage pipeline of Claude Code subagents that turns 345 undocumented Oracle report queries into a governed warehouse model — profiled, graphed, collapsed, keyed, mapped column-by-column, and shipped as executable SQL. Every stage is checked by a second, adversarial agent before the next one is allowed to start.

The problem

The schema was never the documentation. The reports were.

Interloop is a hosiery manufacturer running a custom Oracle 11g application — HMS, the Hosiery Management System — across the full sock lifecycle: order, knitting, toe closing, dye house, boarding, packing, warehouse, shipment. The system works. Nothing about it is written down.

There is no ER diagram, no data dictionary, no glossary. Most tables declare no primary key. Most relationships that actually matter are not declared as foreign keys at all — they exist only as join predicates inside Oracle Reports (RDF) queries. Two schema eras still run side by side: pre-2008 legacy PRD_ORDER_* tables and the post-2008 HOMS/SMPL revamp. The business rules — which status codes count, which rows are excluded, how a quantity is derived — live inside view DDL and report SQL, not anywhere a modeller can read them.

The raw material handed over was 345 consolidated report SQL files in 15 folders, a signed SOW, 11 discovery-session transcripts, 9 business-process design documents, and read access to the production database. The deliverable was a governed model that 3–5 business users could self-serve against in Tableau, on S3 and Redshift.

So the pipeline reads the system the way the system actually describes itself: it mines the report SQL for what joins to what, profiles the live catalog for what the data really looks like, and only then decides what the entities are.

The folders were not the business

The 15 input/SQL/ folder names (fgs, orders, work_order, management…) are how somebody organised files on the day of handover — not process boundaries. Reading the 9 BPD documents produced a different, evidence-backed answer: 12 real business processes plus a global shared master-data layer. orders split into Reservation Orders and Sales Order & Delivery; work_order dissolved across four processes; management turned out to be a cross-stage KPI rollup owning nothing.

Taking the handover's own filing system as ground truth would have baked somebody's folder habits into the warehouse.

The mechanism

A second agent that is paid to disagree

The pipeline's one non-negotiable rule is that no stage signs off on its own work. After a stage agent writes its output/, a separate Feedback Agent runs against that stage's hand-written criteria.md — and, critically, against the primary sources: the SOW, the raw SQL, the live Oracle catalog. It is explicitly forbidden from grading the draft on the draft's own account of itself.

It writes verdict: approved or verdict: rejected. A rejection carries required_fixes, and nothing downstream may route around it.

It caught things, repeatedly

On Phase 00 it independently re-read the SOW and all 11 meeting-note files and confirmed an internal SOW contradiction, an acronym collision, and a mislabeled source file. On Phase 01 it took five rounds: two real gaps — a classification-bookkeeping defect that silently dropped 10 tables from profiling, then a sibling stale-profile-file gap — had to be fixed before the final round held. On Phase 02 it found a CTE leak in a regex-fallback path and an alias-resolution blind spot for correlated subqueries. On the LDM it caught a uniqueness check that was vacuously true on a zero-row table.

The gate got finer-grained as the work got finer-grained

Reviewing a whole phase at once stopped being useful once modules were being reworked one at a time. The rule in CLAUDE.md changed to make any discrete deliverable gate-worthy: a single module's silver lock, a keys-and-load-strategy pass, one gold mart set. There are 26 approved review files on disk under pipeline/*/feedback/; several needed a round-1 rejection first (the Toe Closing gold marts were rejected for overclaiming report coverage, Processing twice for stale context files).

The whole-phase review.md files for stages 01–06 are deliberately empty — explicit, logged skips while per-deliverable review carried the load. That is recorded as a known state, not hidden as a pass.

01

ISD — Information Source Document

5-round review

Which tables really exist, who owns them, and what does the data actually look like?

Six mechanical steps, three of them against the live database. Parse all 345 SQL files for table references; resolve every synonym, view and dblink chain through the Oracle catalog; classify each object's role and owning process; reconcile tables claimed by more than one process; then profile keys, columns, nullness and distinct counts per table.

The extraction alone needed real judgment. sqlglot correctly parses FROM achieved_parts as a table reference — but a CTE name is query-local and will never resolve to a catalog object. 74% of the first resolution run came back UNRESOLVED for exactly that reason. Excluding CTE names cut the raw inventory from 2,236 to 685 candidates before a single minute of database time was spent on them.

Tables that cannot be confidently assigned an owner are marked ambiguous-needs-review and carried forward flagged — never silently dropped, never assigned a guessed owner.

Extended ISD

2-round review

What do these tables actually mean to each other, that the catalog never declares?

Phase 01 established that most HMS tables declare no PK or FK, and that a declared PK is often a surrogate masking a different true grain. This stage recovers the relational layer from where it really lives: the join predicates in the report SQL, and the business logic embedded in view DDL.

7,834 join predicates extracted statically produce 820 distinct relationships. Oracle's own declared FK constraints are then reconciled in and given precedence — a declared constraint outranks a report happening to join two tables. Join-pattern mining alone had missed 185 of 425 in-scope declared FK pairs outright.

Grain inference is deliberately cheap: live COUNT(DISTINCT…) verification is reserved for genuinely ambiguous candidates only. Some of these tables hold 35M+ rows; a blanket sweep across 446 of them would be a production incident, not a profiling pass.

Entity Graph & Schema Modelling

inserted mid-project

What does the whole relationship graph look like at once — and what shape does each cluster naturally have?

This stage did not exist originally. It was inserted after the CDM was found to be making structural calls — which tables collapse into one entity, which are shared — one business process at a time, without ever seeing the rest of the graph. Every stage below it was renumbered and rebuilt.

It assembles 632 nodes and 887 edges: one node per classified table, plus one for every table reached only via a join or FK and never profiled at all. Those 229 unresolved nodes are kept and tagged profiled: false — dropping them would make the picture look cleaner than the system is.

From that graph it decides four things corpus-wide: connected clusters, schema shape (star / snowflake / normalized, ranked by total graph degree rather than declared FK fan-in), structural collapse groups, and reusable/conformed entities. Union candidates get two independent passes — a mechanical column-signature Jaccard check, and an agent-driven semantic pass for tables that mean the same thing under different column names.

CDM — Conceptual Data Model

validator 47/47

What are the business entities per process, with no physical detail yet?

Consumes Phase 03's collapse, conformance and union decisions rather than recomputing them, and turns 387 physical tables into 303 conceptual entities — 62 of them collapsed from more than one table. 141 are conformed (referenced by two or more processes); 292 carry a grounded business name.

One diagram per business process, generated programmatically as draw.io mxGraph XML from structured JSON — plus a hand-rolled force-directed layout and a dependency-free HTML viewer, because these diagrams describe real client schema and had to stay usable offline.

Diagram scope is the interesting constraint. A process's diagram shows only its own entities plus global-owned entities it genuinely connects to. Every other real cross-process edge is recorded in cross-process-relationships.json instead of drawn — 215 of them — so the evidence survives without the picture becoming unreadable.

LDM — Logical Data Model

7 modules hand-locked

What is the keyed, grain-correct dimensional model an ETL build can actually be written from?

This is where Hub/Dim/Fact classification, natural vs surrogate keys, SCD strategy and load strategy get decided. It runs from a supplied ldm-builder.md skill plus eight project override rules that take precedence wherever the two conflict — no Hub construct at all, SCD2 with a stored effective_date, CDC-vs-full-load decided by transaction-date presence, and a Fact key built from the actual source PK.

Each CDM entity is grain-decomposed: one conceptual entity can legitimately become a Dim plus two Facts if its collapsed tables sit at different grains. Facts that represent the same event across sibling tables are merged into UNION ALL branches — 17 of them — scored on confidence, with structural vetoes that outrank the score.

The model got smaller as it got better. The mechanically generated build produced 330 entities. Running each process through a BPD-vs-model lock, an entity-by-entity scorecard and a keys/load pass brought it to 229 — header/detail pairs correctly folded, out-of-programme tables dropped, billion-row audit logs kept out of silver. Six processes are now hand-authored and locked against regeneration; the other seven stay generator-built, with every borderline call flagged.

SMX — Source-to-Model matriX

0 open items

Where, physically, does every single column in that model come from?

The handoff artifact for the ETL build: one row per destination column, carrying destination schema/table/column, key role, transformation, joining condition, and source column/table/schema. 4,543 rows across 14 workbooks — one per business process, plus a shared workbook for the 23 entities used by two or more processes, mapped exactly once.

Nothing is allowed to be vague. A merged Fact maps one block per UNION branch, and a column a branch does not have gets an explicit NULL — column not present in this branch row rather than being omitted — a missing row and a NULL-by-design row mean very different things to whoever builds the pipeline. An FK promoted from inferred join evidence is labelled [join inferred, high confidence — verify] so nobody mistakes SQL evidence for a catalog constraint. A source schema with no Bronze mapping is a hard error, not a fallback.

Alongside each workbook, 229 executable Spark SQL files are generated from the same module JSON, so the mapping and the reference implementation cannot drift. Execution order is parsed from the emitted SQL's own FROM/JOIN clauses — 3 waves, 225 real file dependencies — rather than from the model's 516 FK edges, because most FKs are raw-value copies that read nothing at runtime. The model graph is denser than the dependency graph, and running against the wrong one would serialise work that could run in parallel.

Data Marts — Gold

7 mart sets approved

What does a business user actually query, and does it cover the reports they have today?

Silver is grain-correct and normalized; it is not what a Tableau user should join by hand. Gold is a small set of wide, self-service marts per process — 47 mart SQL files across 11 process folders — each with an explicit grain, a data dictionary, and a client-facing Excel workbook generated from the same source.

The discipline here is coverage honesty. Every legacy Oracle report is tracked in REPORT-COVERAGE.md as Covered, Partial or Gap — and a report is only flipped to Covered when the mart genuinely carries the formula at the right grain. One knitting on-time-delivery report was moved back to Partial after the user pointed out the mart and the original RDF sit at different grains. Claiming coverage that a grain mismatch quietly breaks is worse than admitting a gap.

Alongside the personas sit the global rules in CLAUDE.md that every session inherits: always use the project virtualenv, always redirect script output to logs/ with 2>&1 (progress bars write to stderr, and a crashed long-running job once lost its whole run's output), and never mark a task complete without either an approved verdict or an explicitly logged decision to skip review.

Judgment calls

Six decisions that shaped the model

137 are logged in memory/decisions.md, each with the alternative that lost and why. These six changed the shape of the output rather than a detail of it.

Collapse on structural facts, never on a heuristic label

Rule · Phase 03

The original collapse rule required a candidate parent to carry a core-transactional role — the pipeline's own guess about the table. It was replaced by a name-family test: a shared leading token stem, an identifiable header in the family, and a child that does not head its own sub-family. Table names and declared FKs are hard evidence; a role label is this pipeline's inference about them.

Rejected: keeping the role filter and patching the cases it got wrong — it had already inverted 7 of 47 groups (see below).

Only a Fact ever holds a key — a Dim holds none, not even another Dim's

Override · supersedes the base skill

Enforced in two passes. A Dim found holding a Fact key is reclassified as a Fact — its identity depends on a transaction, which makes it a child of that transaction. A Dim holding another Dim's key has that key demoted to a denormalised plain attribute: the parent's value, not a joinable reference. Dimensions meet only at the Fact.

Rejected: the supplied skill's own rule 4, which permitted a Dim to carry another Dim's key plus its name and description.

A cross-process edge is recorded, not drawn

Scope correction · Phase 04 & 05

The original rule — any real edge pulls the other side onto the diagram as a placeholder — let corpus-wide hub tables drag unrelated processes onto diagrams that had nothing to do with them. It surfaced from a single user observation: a production-planning trial-run table appearing on the orders diagram off a three-occurrence FK. Now a diagram shows only its own entities plus global ones it genuinely touches; all 215 other real edges go to a report file.

Rejected: deleting the edges, which would have lost real evidence to make a picture tidier.

Hand-author the modules that matter; generate the rest and say so

Process · Phase 05

Six processes — Toe Closing, Processing, Finishing, FGS, Waste, Packaging — were rebuilt entity-by-entity against their BPD document, with live grain probes and a scorecard per entity, then locked so the mechanical generator cannot overwrite them. The remaining seven stay generator-built, with every borderline Dim-vs-Fact call listed in classification-review.md, sorted least-confident first.

Rejected: presenting the heuristic output as final. The user's objection — “heuristic silver is not final” — is what started the entity-review cycle.

Include the ambiguous, flag it, never guess an owner

Standing rule · every phase

52 tables could not be assigned an owning process from the evidence available. They stay in the graph and, collapsing to 50 entities, in the entity roster — flagged contains_ambiguous_table with a null owning domain, and therefore modelled in no per-process LDM module rather than forced into a guessed one. An FK pointing at one of them resolves as unresolved: true with the raw ID carried through, never as a fabricated join.

Rejected: dropping them (loses real tables) or assigning a best-guess owner (fabricates a fact the diagram then presents as settled).

Two passes for union candidates, because one is structurally blind

Method · Phase 03

The mechanical pass compares column signatures by Jaccard overlap and requires provable absence of any edge between members — it finds the same entity split by year or plant. It cannot see that AUTH_DATE and BLOAD_DATE mean the same thing across two tables with 0% name overlap. So a second, agent-driven semantic pass runs over a mechanical worklist, and every claim must cite a specific column correspondence.

Rejected: lowering the Jaccard threshold, which produces noise rather than the missing class of match.

Failure journal

What broke, and what it changed

Every mistake is written up in memory/failure-journal.md with how it was found and how it was fixed — so the same class of bug is not re-derived in a later stage. Four of the most expensive.

A 10-row lookup swallowed a 15.8-million-row transaction table

The collapse rule filtered candidate parents by role before testing “exactly one qualifying parent.” When a detail table's real header happened to be tagged shared-reference, the filter did not skip that candidate — it removed the right answer from the candidate set, leaving an unrelated small lookup as the sole survivor, which then passed the uniqueness test as unambiguous. 7 of 47 entities came out inverted.

Nothing caught it because every build step verified its own contract and all of them passed: all 392 tables covered exactly once, every entity modelled, counts reconciling. Nothing asserted that a group's members are the same business object — that was assumed, not checked. It surfaced four stages downstream as four unrelated-looking symptoms.

A filter that runs before an ambiguity test does not reduce the candidate set — it rewrites the answer.

The validator that should have caught it was a zero-byte file

validate_cdm.py was listed as a runbook step. It was empty. It exited 0 and printed nothing, which reads exactly like success. It is now 47 real checks — and it deliberately re-implements the name-token split in five lines rather than importing the library it validates, so a bug in the tokenizer cannot validate itself.

Write the validator for the assertion you are assuming, not the one you are computing. An empty validator is worse than no validator.

A uniqueness check that was true because the table was empty

Cardinality resolution compared COUNT(*) to COUNT(DISTINCT …) per side with no lower bound. WMS.CRTSTATUS has zero rows, so 0 == 0 held for any column asked of it — silently promoting 3 pairs to 1:1 (confirmed) on no evidence whatsoever. The Feedback Agent caught it by treating a clean result as something to interrogate, then confirmed the empty table live.

Any “for all X, P(X)” check needs an explicit empty-set case, or it passes vacuously and looks confident doing it.

Several FKs pointing at one parent were ANDed into a join that could never match

A composite-FK grouper treated any two FK entries pointing at the same target as one composite key and ANDed their columns into a single predicate — breaking role-playing dimensions, where a locator dimension is legitimately referenced three times (bin, from-bin, to-bin) by three separate FKs. 12 entity/target pairs across 8 modules. The mechanical validator had nothing to say about it: the SQL was syntactically valid and simply wrong.

It was found by grepping the model for the general shape of a bug the agent persona named one specific instance of — not by trusting the validator.

The pattern across all four is the same, and it is the reason the gate exists at all: every build script verifies its own step, so none of them can see a defect that only appears once the steps are composed. Both cross-phase validators — validate_cdm.py and validate_dimensional_ldm_smx.py — read only the final artifacts and know nothing about how they were produced, precisely so they can.

What is deliberately not finished

Seven of the thirteen LDM modules are still generator-built rather than hand-locked, with their borderline Dim-vs-Fact calls listed for review but not yet reviewed. How it is built

Repository shape and operating rules

Everything is plain files under version control. There is no orchestration service and no database of state — a stage's inputs are the previous stage's committed output/, and a stage's memory is markdown a future session can read in one pass.

The four memory files are load-bearing rather than decorative: decisions.md records the judgment call and the alternative that lost; learnings.md records what worked and should be repeated; failure-journal.md records what broke and how; session.md records what happened in each working session and what the next one should do first. A brand-new session with no transcript can reorient from those four plus CLAUDE.md.

Claude Code subagents for every stage and every review. Python 3 in a project virtualenv: python-oracledb in thick mode (11g will not accept a thin client), sqlglot for SQL parsing, openpyxl for the SMX workbooks, networkx for the spine/branch analysis, tqdm for progress. Diagrams are generated draw.io mxGraph XML with a hand-rolled force-directed layout and dependency-free HTML viewers. Target platform is S3 → Redshift → Tableau, with the generated silver SQL written for the AWS Glue Spark SQL dialect against a Bronze / Silver / Gold catalog.
