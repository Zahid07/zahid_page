How the Simple Store lakehouse works

An e-commerce OLTP system writes to MySQL. A config-driven Airflow mesh then pulls those tables through Trino into a Delta Lake medallion, builds a Kimball star, serves ClickHouse aggregations, and forecasts the next five days of product demand.

01

The problem

The course asks for a full data-driven architecture: ingestion, processing, a warehouse, a dashboard, a shareable data product, and logging. The domain is a two-sided store. Customers browse and order. Merchants manage catalog and stock. That operational system is real — FastAPI, React, MySQL — and it is also the source of truth for everything downstream.

Analytics cannot live in that MySQL. The OLTP schema is 3NF (customers, merchants, products, orders, order_items). It mutates. It has no surrogate keys, no grain contract, and no place to hang a five-day forecast. The lakehouse exists to freeze those mutations into layers that can be replayed, modelled, and served.

Operational

Simple Store

React + Vite frontend, FastAPI backend, SQLAlchemy against the shared inventory database. Customer and merchant modes, cart, stock, live /api/analytics/* from OLTP.

Ingest

Two ways out of MySQL

Debezium CDC into Kafka for change events. Airflow + Trino incremental MERGE for the lakehouse. They share the database; they do not share a consumer.

Serve

Gold in two stores

Delta Lake on MinIO holds the Kimball tables. ClickHouse ReplacingMergeTree holds the same gold plus semantic marts, quality audits, and forecasts.

02

Architecture

Five Docker Compose projects sit next to each other: dummyData, simpleStoreSetup, kafkaSetup, pipelineSetup, trinoSetup. They talk over host ports and a couple of named networks. The compute that actually moves rows into the lake is Trino SQL, scheduled by Airflow, not Spark.

What the code does vs what a README can claim

Folder READMEs mention Spark, Kafka-to-bronze streaming, and PostgreSQL as the home of facts and dimensions. The DAGs do not. Bronze and silver are Trino SQL against mysql.inventory.* and delta_lake.bronze|silver.*. Gold facts and dims are written to Delta Lake, then copied into ClickHouse. PostgreSQL in this repo backs Airflow, Superset, Conduktor, and the Hive metastore — not the star schema.

03

The staged pipeline

Five entities travel together. Each has a bronze DAG and a silver DAG. Gold is five transformer DAGs whose task lists live in MySQL, not in Python. Semantic marts, a forecast, and quality checks hang off Airflow Datasets so the graph is data, not cron luck.

01

Seed and operate

dummyData · simpleStore

generate_dummy_data.py inserts a default of 100 customers, 25 merchants, 250 products, 400 orders (1–5 items each) into inventory. A CSV twin writes the same shapes to dummyData/csv_output/. mysql-init.sql also plants a tiny demo catalog so the app works before the generator runs.

Simple Store is the data product: customer signup, cart, checkout, merchant CRUD, order status, and dashboard stats. Writes go to the kafkaSetup MySQL on the external network kafkasetup_default. updated_at columns are what the lake uses as a CDC watermark — even though that load is JDBC, not Kafka.

02

Capture change events

Debezium · Kafka

MySQL is configured for CDC in mysql.cnf: binlog_format=ROW, binlog_row_image=FULL, GTID on. A dedicated replication user is created at init. The connector mysql-connector uses ExtractNewRecordState, JSON without schemas, and snapshot.mode=initial.

Topics are dbserver1.inventory.{customers,orders,products,order_items}. Merchants are not in table.include.list — merchant rows still reach the lake through Trino, they just do not appear as Kafka events unless the include list is extended. Conduktor is the inspection UI. Airflow never consumes these topics.

03

Bronze — incremental MERGE

5 ingest DAGs

Each bronze DAG is the same shape: start_task → read_job_config → ensure_tables_exist → load_to_staging → merge_to_main → update_watermark → end_task. Config comes from pipeline_jobs (is_cdc, watermark, batch size). Column types come from table_columns.column_map. Table DDL comes from table_ddl. SQL is generated by utils/sql_builder.py — no column names are hardcoded in the DAG files.

Load is INSERT INTO delta_lake.bronze.<table>_staging SELECT … FROM mysql.inventory.<table> with WHERE updated_at > last_cdc_value after the first run. Then a Trino MERGE on the natural key (order_id, product_id, id, merchant_id, item_id). Unregistered MySQL columns are packed into _additional_attributes as a JSON string so a new source column cannot break the job.

04

Silver — flatten overflow, keep types

5 transform DAGs

Silver DAGs wait on the bronze Dataset (/opt/airflow/datasets/bronze_*.txt). They discover JSON keys in _additional_attributes, ALTER TABLE the silver Delta table if a key is new, extract with JSON_EXTRACT_SCALAR, and MERGE into delta_lake.silver.<table>_silver. Registered columns keep their mapped types. Promoted extras land as VARCHAR.

That is the schema-evolution contract: bronze never fails on unknown columns; silver eventually makes them queryable; gold SQL still only projects the modelled attributes.

05

Gold — helpers, dimensions, facts

5 transformer DAGs

Each gold DAG file hardcodes only a DAG_ID matching pipeline_jobs.job_id. Tasks are rows in pipeline_tasks, ordered by sequence. SQL files live under airflow/jobs/. Python follow-on tasks load the resulting Parquet from MinIO into ClickHouse via the HTTP s3() table function (run_pipeline_task_sql.py).

Dimensions are Type 1: HLP inserts a new surrogate for a new natural key; DIM MERGEs attributes and sets oper = 'U' on match. Facts are insert-only for unseen natural keys, with SUM(1) OVER (ROWS UNBOUNDED PRECEDING) against MAX(sk) to mint surrogates. Line total is quantity * price. Date keys are CAST(DATE_FORMAT(order_date, '%Y%m%d') AS BIGINT).

06

Semantic, forecast, quality

ClickHouse

Merchant marts: revenue overview, revenue by month, AOV by quarter, product performance, stock vs sales, customer reach. Customer marts: favourite merchant, lifetime value, order-frequency buckets. All are INSERT INTO gold.* SELECT … FINAL JOIN against ClickHouse gold copies.

orders_forecast_dag fits scikit-learn LinearRegression per (merchant_sk, product_sk) on 90 days of fct_order_items quantity, writes five future days to product_sales_forecast_5d, then denormalises names into product_sales_forecast_5d_norm. Short series fall back to the historical mean. Quality then records null percentages and business metrics (total sales, order count, AOV, units sold, inventory units) into quality_test.

04

Star schema

The model is Kimball with an explicit helper table in front of every dimension. The HLP is the only place a natural key becomes a surrogate. Facts never join silver on customer_id; they join HLP. That keeps Type 1 rewrites on the DIM from scrambling fact keys.

05

The control plane

Airflow is not the source of truth for “what runs when.” MySQL database pipeline_configs is. DAGs parse it at load time, resolve an Airflow Dataset name and a dependency list, and either schedule on cron or on those datasets. Adding a gold task is an INSERT into pipeline_tasks, not a new Python file — unless you need a new entity, in which case you copy the transformer template and change DAG_ID.

Tables in pipeline_configs
  • pipeline_jobs — name, schedule, is_cdc, last_cdc_value, JSON parameters
  • pipeline_tasks — file_path, sequence, params for gold/semantic
  • table_columns — JSON column_map used by sql_builder
  • table_ddl — CREATE TABLE for bronze Delta tables
  • dataset — Airflow Dataset name + comma-separated dependencies
  • ingestion_runs — start/end, status, rows, error_message
Schema evolution

Bronze: extras → _additional_attributes JSON. Silver: distinct JSON keys become VARCHAR columns; missing ones get ALTER TABLE … ADD COLUMN before MERGE. Gold SQL is explicit and does not auto-project overflow keys — modelling stays a decision, not an accident.

Stack, as it actually runs

simpleStoreSetup

React 18 + Vite 5, FastAPI 0.104, SQLAlchemy 2, PyMySQL. Frontend :3000, backend published :8001. Shares kafkaSetup MySQL. Analytics endpoints recompute KPIs on OLTP, not ClickHouse.

dummyData

Python generator (pymysql) and a CSV writer. Defaults 100 / 25 / 250 / 400. Dockerfile for a one-shot loader on host network.

kafkaSetup

MySQL 8.0, Debezium Kafka + Zookeeper + Connect, Conduktor, Postgres for Conduktor. Redis, MinIO, ClickHouse, MailHog exist in compose but are commented out here — MinIO/ClickHouse live under trinoSetup.

pipelineSetup

Airflow 2.8.1 (custom image: pymysql, trino, clickhouse-connect, numpy, pandas, scikit-learn), Postgres :5435, Superset :8088 + Redis, Timeplus :8000. DAGs under airflow/dags, SQL under airflow/jobs.

trinoSetup

Active docker-compose.yml starts ClickHouse 23.8 (:8123). The lakehouse cluster — Trino, Hive Metastore, MinIO, metastore Postgres — is in docker-compose_no.yml. Catalogs on disk: delta_lake, mysql, clickhouse, postgresql, hive, iceberg, minio.

Trino catalogs that the pipeline uses: mysql (source), delta_lake (medallion on MinIO via Hive Metastore), clickhouse (available for federated SQL). Iceberg and Hive catalogs are configured; no DAG writes Iceberg tables. ClickHouse gold tables use ReplacingMergeTree(_ver) or ReplacingMergeTree(generated_at) so later loads win.

07

Design decisions worth keeping

Trino is the ETL engine

One SQL dialect moves data between MySQL, Delta, and (when needed) ClickHouse. Airflow’s job is schedule, XCom, retries, and run metadata — not Spark submit. That matches a laptop-sized Docker lab better than a cluster.

CDC and lake load are not the same pipe

Kafka proves that every OLTP mutation is observable. The lake load is a watermarked MERGE so replay is a SQL statement, not a consumer-group offset. Different failure domains.

Config in MySQL, code in templates

Column maps, DDL, schedules, Dataset edges, and gold task lists are data. Five bronze DAGs and five silver DAGs look repetitive on purpose: the variation is in pipeline_configs, not in forked logic.

HLP before DIM

Surrogate assignment is a separate insert-only table. Facts bind to *_sk. Attribute updates do not rewrite fact rows. Product waits on merchant because product_dim.merchant_sk is a dimension-to-dimension key.

Overflow JSON, then promote

_additional_attributes is the safety valve for source schema drift. Silver is where keys become columns. Gold stays a modelled contract.

Two analytics planes

The store UI answers “what is happening in my shop right now” from MySQL. Superset / ClickHouse answer “what was true in gold after the last successful DAG.” That split is honest: the data product does not pretend the warehouse is synchronous.

Forecast is a serving table, not a notebook

Same Dataset chain, same ingestion_runs bookkeeping, ClickHouse ReplacingMergeTree so a new batch supersedes the last. Model: linear trend on day index, mean fallback, zeros for missing days.

Quality is a DAG, not a screenshot

Null audits and sales metrics land in quality_test after forecast, so a broken gold load is visible as rows, not only as an Airflow square.

Intentionally not claimed

Spark jobs, Kafka sinks into Delta, PostgreSQL as the fact store, Iceberg tables, and Timeplus as a gold writer do not appear in the DAGs or job SQL. They show up in compose comments, extra catalogs, or rubric READMEs. The running architecture is Trino + Delta on MinIO + ClickHouse + Airflow Datasets.

08

What was implemented

End-to-end lab for the course rubric: a working store, seeded OLTP, Debezium CDC, a medallion lakehouse, a Kimball gold layer, semantic marts, a demand forecast, quality logging, and dashboards — all locally on Docker.

  • OLTP schema, FastAPI contracts, and dual-mode React UI against the shared MySQL.
  • Binlog CDC with a registered Debezium connector and Conduktor inspection.
  • Schema-driven bronze/silver Trino pipelines with watermarks, MERGE, and run metadata.
  • Gold HLP/DIM/FCT SQL, MinIO → ClickHouse copy, Dataset-ordered transformers.
  • Nine semantic marts, 5-day product forecast, null and sales quality tables.
  • Trino catalogs, Hive Metastore, MinIO buckets, ClickHouse init DDL, Airflow custom image.
